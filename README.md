## 这份记录的价值在哪

性能工作最容易浪费的地方不是「优化得不够快」，而是**反复走同一条错路**。
所以这里写得最细的是三件事：

1. **哪条路已经被证明走不通**（SUMMARY 第 4 节，9 条）；
2. **测量方法本身怎么才可信**（第 5 节：归一化、多采样、分位数、分桶）；
3. **怎么判断「到底有没有变快」**（判据与陷阱，见第 11 节的事故记录）。

## 三个最有用的结论

### 1. 黑屏的真根因（可复现的因果链）

翻译器侧任何改动都会让着色器缓存条目失效 → 运行时现场翻译并写回缓存 →
在某些环境里写缓存被拒（`os error 5`）→ **该着色器的管线全部被丢弃** →
窗口标题显示 `0 draws/frame` → 黑屏。

**规则：改翻译器之后必须先重建缓存再跑。** 这条把「黑屏」从玄学变成了操作流程。
证据与前后对照见 SUMMARY 第 1 节。

### 2. 唯一一次两倍收益：关掉稀疏驻留

把 `VICTORY_LEVELS_ON_DEMAND` 的默认值从 `1` 改为 `0`：

| | 开（旧默认） | 关（新默认） |
|---|---|---|
| fps 中位 | 5–6 | **12–14** |
| 轻场景 fps | — | **23–25**（标题自身上限 30） |
| 每 draw 成本 | 65–67 µs | **28–34 µs** |
| 专用显存 | 15.9 GB | **12.1 GB** |
| 共享显存 | 7.1 GB | **6.3 GB** |

三次独立运行、分布不重叠，**不改动任何画面**（只改驻留策略）。
原因：tiled 资源每次首次使用都要等映射——实测整场 29,000 次等待、合计 21.6 秒、最长一次 728 ms。

### 3. 30 fps 的差距是一笔清楚的账

重场景（3,000+ draws）下提交线程每帧 57.6 ms：

| 项目 | ms |
|---|---|
| `lists' steps`（其中真正的数据搬运 **1.1**） | 16.7 |
| `waiting for flights` | 14.2 |
| `copies in the card's memory` | 11.4 |
| 其余（写监视、上送、计划步骤等） | 15.3 |

**98% 是记账与等待，不是搬数据。** 要到 33.3 ms，需把前两项各砍 70%——
这是结构性重构的量级，不是调参。轻场景（500 draws）已经跑到 23–25 fps，差距全部在重场景。

## 怎么复现

环境：Windows + 一张支持 Shader Model 6.6 与 mesh shader 的 D3D12 显卡。

```powershell
# 构建
cargo build --release -p victory --features diagnostics

# 重建着色器缓存（改了翻译器之后必须做，否则黑屏）
victory.exe shaders <标题目录>

# 跑并测量：加载 → 按 A 出标题 → 固定按键路线 → 固定时刻截图
powershell -File walk.ps1
```

判据是**窗口标题里的 `N fps M ms/frame K draws/frame`**：
`0 draws/frame` = 黑屏；上千 = 已经在游戏内。

### 关键陷阱（都踩过）

- `VICTORY_KEYS` 的语法是 **`起-止:键`**（区间在前）或 `时刻:键`（按住 0.2 秒），
  时间是**从标题进程启动算起**，不是从第一次按键算起；
- 没有真实手柄时必须有「替身手柄」，否则脚本按键完全失效；
- 不同运行的 draw 数可以差 2 倍，**直接比 `ms` 没有意义**，要归一化到 `µs/draw` 并分桶；
- 单点采样在场景不受控时测不出 5% 的差异——同一个 draw 区间内 p25 到 p75 本身就能差 2–3 倍。

## 最近一阶段的结论（2026-11）

三条修好的，两条到头的。

**修好的：**

1. **几何阶段的"挂死"其实是默认线程数缺陷。** `translate` 默认按逻辑核数起线程，
   每线程约 800 MB（校验器 + 翻译工作集）；28 核机器上 22.5 GB，被推进页面交换，
   表现为"CPU 零增长"。默认收敛到 8 之后，`VICTORY_GS=1` 的 `translate --validate`
   从"跑不完"变成 180 秒跑完，几何 **195/195** 通过。
2. **着色器缓存忘了开关。** 缓存指纹里那份开关清单是手写的 12 个名字，
   而 `build.rs` 早就扫描源码生成了完整清单，只是没被接上——于是切换 `VICTORY_GS`
   会被喂另一个状态的条目。改为使用自动清单后，"换开关"与"清空缓存"结果一致。
3. **缓存写不进去就丢着色器。** 写盘失败（`os error 5`）被当成"无法翻译"向上抛，
   那个程序的所有 draw 被丢弃。改为降级为无缓存翻译：实测让 1,977 次写失败发生于一次运行，
   游戏仍画出 4,041 draws/frame。

**到头的：**

4. **拆窄刷新区间（`VICTORY_REFRESH_GAP`）无收益。** 确定性基准给出页数 −71%，
   真机是 `refreshes` 13.2 → 16.9 ms（变差）、检查数 +23%、页数不降。保持默认关闭。
5. **`refreshes` 这条路径的天花板只有零点几毫秒。** 在能复现争用的基准上量出：
   一次"是否有待写入"的查询，原子读 11.9 ns、取锁 30.4 ns（2.5×），
   整条 walk 无争用时 6 ns/step。按每帧约 14,000 次查询算，可回收上限约 0.3 ms，
   而重场景每帧 57.6 ms。**继续磨这条路径没有意义**，要动就动
   `copies in the card's memory`（11.4 ms）或 `waiting for flights`（14.2 ms）。

方法上有一条值得记：同一批日志，只看最后 3 行判"无效"，改取全部样本中位数后是 −40%；
而那个 −40% 后来又因为分母（step 数随场景变化）不可比被撤回。
**指标口径错了，后面的结论全部作废** —— 这是本阶段最贵的一课。
